## The stack

```
                 www = 172.29.22.100 (a VIP)
                          │
              lb1 ────────┴──────── lb2        HAProxy + keepalived
                 └──────┬───────┬──────┘
                      web1     web2            the shop, twice
                 ┌──────┴───┬───┴──────┐
                pg1  ───▶  pg2      etcd1 etcd2 etcd3
              primary    replica
```

You work in `ops`, which sits on both networks. Everything you configure is a
file under `/ha`, shared with every node. The load balancers and app nodes
notice their files change and reload within a second. etcd members are the
exception: each reads `/ha/etcd/<member>.env` only when it starts, so
`docker restart` or `node start` applies a change there.

`node` is how you break things yourself:

```
node kill web1          crash it
node pause lb1          hang it: frozen, still holding its addresses
node resume lb1
node start web1
node cut web2 back      partition it from the back network
node heal web2 back
node ls
```

`gapwatch 20` requests `http://www/` every 50ms for 20 seconds and reports
the longest run of failures. That number is what a user sees.

## What you'll be able to do

- Put two servers behind one name and prove either can die
- Find every single point of failure by breaking each box, not by reading the
  diagram
- Measure a failover instead of trusting its default, and tune it to a budget
- Keep sessions alive across a node loss without pinning users to a node
- Write a health check that tells the load balancer the truth
- Promote a replica with no acknowledged write lost
- Explain why a three-member cluster with one survivor must refuse writes
- Elect one leader through a partition, with a lease that is renewed before
  every action
- Serve the last good answer, labelled as old, when a dependency is down
- Fail back after a split without losing either side's writes
- Rotate a certificate on every node behind an address, not just the active one
- Build a way in that still works when the thing it repairs is down

## Before you start

`ha-stack` runs ten small containers: two load balancers, two app nodes, two
Postgres instances and three etcd members, plus `ops`. The first start builds
four images and takes a few minutes. After that it starts in about twenty
seconds.

`ops` holds the Docker socket, so `node` can stop and partition the other
containers. Treat it like any shell with Docker access.
