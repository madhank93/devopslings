## What you'll be able to do

- Read a continuous profile from production, diff two releases' flame graphs,
  and measure what the profiler itself costs
- Find where a slow, idle service is waiting with off-CPU and wall-clock
  profiles, and where its memory goes with `memleak`
- Answer questions about a live box with bpftrace one-liners that hold up on
  any kernel, and write longer bpftrace programs — a uprobe on one function, a
  rule that tells a reverse shell from a cron job
- Use the libbpf-tools — `execsnoop`, `opensnoop`, `runqlat`, `biolatency`,
  `offcputime` — to see the events and distributions that `top`, `iostat` and
  averages hide
- Trace a process that fails silently or starts slowly with `strace`, read a
  deadlock with `py-spy dump`, and take a crash apart from its core in `gdb`
- Debug a container with no shell from the outside, and read a task stuck in
  `D` from its kernel stack
- Write an eBPF adoption policy backed by evidence about kernels, privileges
  and overhead

## Why these

Most production debugging stalls at the same point: the metrics show a
symptom, and the next step is a guess — restart it, add logging, raise a
limit, redeploy with more instrumentation. Each of those changes the thing
being investigated, and most need a change window.

The tools in this module do not. A profiler samples a process as it runs; a
kernel probe sees every syscall, exec and retransmit without the process
knowing; a debugger reads a hung interpreter or a dead process's core. The
habit this module builds is reaching for one of them before reaching for a
restart, and then confirming the fix with the same tool that found the cause.

## The sandboxes

Most lessons run on `linux-box` from module 01, privileged so it can load BPF
programs, with libbpf-tools, bpftrace, `perf`, `strace`, `ltrace`, `gdb` and
`py-spy` installed. The continuous-profiling lessons run on `obs-stack` from
module 18, which adds Pyroscope next to Grafana and Tempo.
`debug-a-distroless-container` runs on your own Docker host.

The box shares its kernel with your Docker host. Some kernels — Ubuntu's 7.0
ones among them — deliver the per-syscall `syscalls:sys_enter_*` tracepoints
to BPF only for CPU 0, so the lessons teach the probes that work everywhere
and say why. bcc's `*-bpfcc` tools do not compile against these kernels'
headers, so every tool here is a libbpf-tools CO-RE binary or a bpftrace
script.

One lesson is blocked: `hubble-flows` needs Cilium on Kubernetes.
