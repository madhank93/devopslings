## The stack

The same `ha-stack` as module 22, with two more machines on the back network:

```
                 www ── lb1 / lb2 ── web1 / web2
                                        │
     pg1 ──▶ pg2      etcd1-3      bao          backupd
   primary  replica               OpenBao      restic REST server
```

You work in `ops`, which has every client tool the module uses: `psql`,
`pg_dump`, `pg_basebackup`, `pg_waldump`, `restic`, `bao` and `tofu`.

Restores need somewhere empty to land. `scratchdb fresh` starts a brand-new,
empty Postgres inside ops on `localhost:5433`; `scratchdb stop` throws it away.

## The shop's recovery objectives

Every lesson that needs them uses the same two numbers, agreed with the
business:

- **RPO 15 minutes** — losing more than the last 15 minutes of orders is not
  acceptable.
- **RTO 60 minutes** — the shop must be taking orders again within an hour of
  the decision to recover.

## What you'll be able to do

- Read a dump and say what is in it, rather than trusting the job's exit code
- State RPO and RTO first, and pick a design that can actually meet them
- Prove a backup by restoring it into an empty server and comparing the data
- Recover to the moment before a destructive statement with WAL archiving,
  without losing what happened afterwards
- Time a restore and reconcile it with the RTO that was promised
- Re-adopt infrastructure into OpenTofu after the state file is gone
- Recognise when a secret store cannot be recovered, and rebuild it honestly
- Keep a backup copy that an attacker with production credentials cannot
  delete
- Write a region-loss plan that uses nothing inside the lost region
- Write the verification job that would have caught GitLab's 2017 outage

## Before you start

Every lesson starts from `ha-reset`, which turns WAL archiving off again and
deletes the module's backup directories. Copy anything you want to keep out of
`/ha` first.
