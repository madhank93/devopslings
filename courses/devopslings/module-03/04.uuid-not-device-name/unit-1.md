---
title: "after the reboot, the backups were written to the scratch disk"
---

## The situation

Two volumes, two `fstab` lines, both correct on the day they were written:

```
/dev/loop0  /srv/backups   ext4  defaults,nofail  0  2
/dev/loop1  /srv/scratch2  ext4  defaults,nofail  0  2
```

```
$ cat /srv/backups/.volume-id
backups
$ cat /srv/scratch2/.volume-id
scratch
```

Correct right now. The device names are the problem, and nothing about them
looks like a problem until the machine restarts.

## Your objective

Make both entries stay correct when the kernel hands out those device names in a
different order.

The check **detaches both volumes and re-attaches them in the opposite order**,
then runs `mount -a` and reads `.volume-id` behind each mount point.
`/srv/backups` must contain the backups volume.

Keep both entries, both mount points, and `nofail`.

## What you're being graded on

The contents behind each mount point after a genuine renumbering — not a config
inspection. The check also rejects any entry still keyed on a `/dev/` path,
because after the swap such an entry only happens to be right.

<details>
<summary>Hint 1 — what a device name actually names</summary>

`/dev/loop0` is not a name for your data. It is a name for a **slot**, assigned
in attach order, reused as soon as it is free.

On real hardware, `/dev/sda` and `/dev/sdb` are assigned as the kernel
enumerates controllers, which depends on probe timing. Any of these reorders
them:

- a reboot where one controller answers a few milliseconds sooner
- a new disk added anywhere in the chain
- a kernel upgrade that changes driver load order
- a disk that fails and is replaced

Nothing about the filesystem changed. What changed is which slot it landed in —
and `fstab` named the slot.

Watch it happen:

```
$ losetup -a
$ umount /srv/backups /srv/scratch2
$ losetup -d /dev/loop0 /dev/loop1
$ losetup --find --show /var/lib/devopslings-vol-scratch.img   # takes loop0 now
$ losetup --find --show /var/lib/devopslings-vol-backups.img   # takes loop1
$ mount -a
$ cat /srv/backups/.volume-id
scratch
```

`/srv/backups` now holds the scratch volume. `mount` did exactly what it was
told; it was told the wrong thing.

</details>

<details>
<summary>Hint 2 — name the filesystem instead</summary>

A UUID is generated by `mkfs` and stored **inside the filesystem's superblock**.
It travels with the data — through a re-cable, a controller change, a move to
another machine.

```
$ blkid
/dev/loop0: LABEL="backups" UUID="7c1f...-..." TYPE="ext4"
/dev/loop1: LABEL="scratch" UUID="a3e9...-..." TYPE="ext4"

$ lsblk -o NAME,UUID,LABEL,MOUNTPOINT
```

Then in `fstab`:

```
UUID=7c1f...  /srv/backups   ext4  defaults,nofail  0  2
```

`LABEL=` works the same way and reads better. It is also easy to duplicate by
accident — clone a volume and you have two filesystems answering to `backups`,
and the mount you get is a race. UUID is the safer default for anything that
matters; label is fine when you control the whole estate.

`PARTUUID=` names the partition rather than the filesystem, which is what you
want for a partition you are about to `mkfs` — it survives reformatting, where a
filesystem UUID does not.

</details>

<details>
<summary>Solution</summary>

```
$ blkid -s UUID -o value /dev/loop0    # backups
$ blkid -s UUID -o value /dev/loop1    # scratch

$ sed -i '\#/srv/backups#d;\#/srv/scratch2#d' /etc/fstab
$ cat >> /etc/fstab <<EOF
UUID=<backups-uuid>  /srv/backups   ext4  defaults,nofail  0  2
UUID=<scratch-uuid>  /srv/scratch2  ext4  defaults,nofail  0  2
EOF
$ mount -a
```

Now the renumbering is irrelevant. Each line names a filesystem, and the kernel
is asked to find whichever device currently holds it.

### Why this is a lesson at all

This is a failure that is invisible until it is expensive, and it does not
announce itself. Nothing errors. `mount -a` succeeds. Both mount points are
mounted, both are writable, both contain a plausible filesystem. The only
symptom is that tonight's backups went to the volume that gets wiped weekly, and
you find out when you need a restore.

Two things worth keeping:

1. **Identify data by something that belongs to the data.** A device path
   belongs to the slot. A UUID belongs to the filesystem. This is the same
   distinction as naming a container by its ID versus its image digest, or a
   deployment by tag versus digest — module 11's `push-pull-and-mutable-tags` is
   this exact argument about registries.

2. **"Correct right now" is not a property worth having.** The original entries
   were verifiably right the day they were written, and the thing that made them
   wrong was not a change anybody made to them. When a config depends on
   ordering nobody controls, it is already wrong; it just has not been observed
   yet.

The wider habit: when something is identified by a name, ask *who assigns that
name and when*. If the answer is "the kernel, at boot, based on timing", it is
not an identifier.

</details>
