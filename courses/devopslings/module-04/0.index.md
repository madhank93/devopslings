## What you'll be able to do

- Say which of several matching routes the kernel will use, and prove it
- Recognise an asymmetric return path, and why the reply never arrives
- Build a container's network by hand — namespace, veth pair, bridge — and then
  name what Docker had been doing for you
- Find the NAT hairpin that makes a service unreachable from itself
- Explain a five-second stall that only exists because IPv6 was answered
- Read an accept queue, and diagnose an outage the application never logged
- Tell a retransmission from a reset from a zero window in a capture

## Why these

Networking failures are the ones where every layer reports success. The route is
in the table. The interface is up. The service is listening. The firewall has a
rule that allows it. Each of those statements is true, and the connection still
does not work — because the thing that decides is not the thing being looked at.

`ip route show` lists routes; it does not tell you which one wins. `ss` says a
socket is listening; it does not say the process stopped calling `accept()`.
That gap between "configured" and "in effect" is the whole module.

## Before you start

Modules 01 and 02. This module runs `netlab`, which is two boxes rather than
one — a routing problem with a single host is not a routing problem.

A note on scope: several lessons build networks inside network namespaces,
which a container genuinely owns. The connection-tracking table is different —
`nf_conntrack_max` is exposed read-only outside the initial namespace, so the
conntrack lesson works on the table's contents and its failure counters rather
than on its size. Where a lesson cannot own something, it says so.
