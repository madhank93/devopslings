## What you'll be able to do

- Take one HTTP request apart into the three steps it actually is, and say
  which of them broke
- Fix a resolver that is slow and intermittently wrong, without touching the
  DNS server
- Explain why `dig` resolves a name and the application next to it does not
- Tell a firewall drop from a firewall reject by the symptom, and read back
  which rule wrote it
- Find an MTU black hole, where the small requests that everyone tests with
  all work
- Verify a certificate chain the way a library does rather than the way `curl
  -k` does
- Turn off SSH password authentication on a live box without losing the session
  you are doing it from
- Make mail from a domain you control authenticate — SPF, DKIM and DMARC are
  three DNS records, and none of them live on the mail server
- Take one failing request down the ladder — frame, next hop, port, name,
  certificate — and name the layer the fault is on before repairing it

## Why these

Every failure in this module happens after the route is correct. The packet
would go the right way if it were ever sent — and it is not, because a name did
not resolve, or the connection was refused before a byte of the request was
written, or the certificate did not verify against a store that `curl -k` was
told to ignore.

The habit this module builds is refusing to say "the network is down". A request
has steps. Each step has its own tool and its own failure signature, and naming
the step is most of the fix.

## Before you start

Modules 01, 02 and 04. This module runs `netlab`, the same two boxes as module
04, with a real resolver on them — a lesson about search domains cannot be
taught with an `/etc/hosts` entry pretending to be DNS.
