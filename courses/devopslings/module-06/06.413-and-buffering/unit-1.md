---
title: "uploads fail at exactly one megabyte, and the app never sees them"
---

## The situation

```
$ head -c 1000000 /dev/zero | curl -s --data-binary @- -o /dev/null -w '%{http_code}\n' http://127.0.0.1/upload
200
$ head -c 1100000 /dev/zero | curl -s --data-binary @- -o /dev/null -w '%{http_code}\n' http://127.0.0.1/upload
413
```

The boundary is suspiciously round, which is the first tell: a threshold at a
power of two is a configured limit, not a resource running out.

The second tell is that the application has nothing to say about it. Not an
error, not a rejected request — no record of the request at all:

```
$ curl -s http://172.32.0.11:8081/admin/received
POST /upload
```

One entry, from the small upload that worked. The large one never reached it.
Something in front refused to pass it on, and that something is the only thing
between the client and the app.

## 413 is the proxy's own answer

`413 Payload Too Large` here is generated by nginx before it opens a connection
to the upstream. The error log says so in as many words:

```
$ tail -1 /var/log/nginx/error.log
... client intended to send too large body: 1100000 bytes, client: 127.0.0.1, ...
```

*Intended to send*. nginx read the `Content-Length`, compared it against its
limit, and answered by itself. The default:

```nginx
client_max_body_size 1m;
```

One megabyte, and `1m` means 1048576 bytes, not 1000000 — which is why the
1000000-byte upload above squeaked through and 1100000 did not.

This is the most reliably misattributed failure in a web stack. The upload is an
application feature, the error arrives while using the application, so the
application is where people look — and the application is the one component
that can prove it was never involved.

## Why there is a limit at all

The limit is not arbitrary caution. It exists because of what nginx does with a
request body by default:

```nginx
proxy_request_buffering on;   # the default
```

With buffering on, nginx **reads the entire body before it contacts the
upstream**. Small bodies live in memory (`client_body_buffer_size`, 8k or 16k);
anything larger is spooled to a temp file under `client_body_temp_path`. Only
when the last byte has arrived does nginx open the upstream connection and
replay the body.

That default buys something real: the upstream is never exposed to a slow
client. A client dribbling out a 25 MB upload over four minutes occupies an
nginx worker — which is cheap, evented, and designed for it — and not an
application worker, which is usually a thread or process and is not.

It also means every concurrent upload is a file on the proxy's disk. Without a
limit, "how much disk can a stranger consume" has no answer. That is what
`client_max_body_size 0` gives away, and why raising the limit is the fix and
removing it is not.

You can watch the trade-off happen:

```
$ head -c 5242880 /dev/zero | curl -s --limit-rate 1000k --data-binary @- http://127.0.0.1/upload
```

Five megabytes at one megabyte a second. With buffering on, the origin does not
hear about the request until second five. With `proxy_request_buffering off`,
it hears about it in the first quarter-second and receives the body as it
arrives.

Neither is universally right:

| | buffered (default) | streamed (`off`) |
|---|---|---|
| slow client holds | an nginx worker | an upstream connection, for the whole upload |
| upstream sees the request | after the last byte | immediately |
| disk on the proxy | one temp file per upload in flight | none |
| upstream can reject early | no — nginx already accepted it | yes, on the first bytes |
| retry to another upstream | possible, body is on disk | not possible, body is already consumed |

Streaming is right when the upstream wants to act on the data as it arrives, or
when uploads are large enough that spooling them twice is silly. Buffering is
right when the upstream is expensive per connection and the internet is full of
slow clients.

## Your objective

1. A 25 MB upload succeeds and the application reports all 26214400 bytes.
2. 64 MB is still refused with 413. A limit has to remain.
3. Uploads are streamed: the application hears about one while the client is
   still sending it. This is measured by uploading at a throttled rate.

Then `/root/answers/upload.md`:

```
rejected_by: <proxy | origin>
limit_bytes: <the limit before you changed anything, in bytes>
```

## What you're being graded on

**The three requirements above, behaviourally.** The 64 MB check is what stops
`client_max_body_size 0`; the throttled check is what distinguishes a raised
limit from a raised limit plus streaming.

**And attributing the 413 correctly.** Saying the origin rejected it, when the
origin's own record shows it never received the request, is the specific mistake
this lesson exists to break.

<details>
<summary>Hint 1 — find out who is answering</summary>

```
$ head -c 2000000 /dev/zero | curl -si --data-binary @- http://127.0.0.1/upload | head -3
$ tail -2 /var/log/nginx/error.log
$ curl -s http://172.32.0.11:8081/admin/received
```

An error page with a `Server: nginx` banner, a matching line in nginx's error
log, and nothing at the origin. Three independent statements about which
component produced the 413.

</details>

<details>
<summary>Hint 2 — the limit, and the reason for it</summary>

`client_max_body_size` is the directive. It defaults to `1m` and can be set at
`http`, `server` or `location` level — put it where the uploads are, not on the
whole server.

Setting it to `0` means unbounded, which the grader refuses. Pick a number that
covers the 25 MB the endpoint is for.

</details>

<details>
<summary>Hint 3 — why the origin hears about it so late</summary>

```
$ head -c 5242880 /dev/zero | curl -s --limit-rate 1000k --data-binary @- -o /dev/null http://127.0.0.1/upload &
$ while sleep 0.5; do curl -s http://172.32.0.11:8081/admin/received | tail -1; done
```

The request appears at the origin only when the client has finished sending.
`proxy_request_buffering` decides that, and it is on by default.

</details>

## What actually happened

Nothing had been configured. Both defaults applied:

- `client_max_body_size 1m` — anything larger is refused by the proxy, and the
  origin never learns it was asked.
- `proxy_request_buffering on` — the body is spooled in full before the upstream
  is contacted.

The repair is two directives on the upload location:

```nginx
client_max_body_size 32m;
proxy_request_buffering off;
```

A number the endpoint actually needs, and a decision to stream rather than
spool — which for a large-upload route is usually the one you want, and is a
trade rather than a free win.

<details>
<summary>Solution</summary>

```nginx
server {
    listen 80 default_server;
    server_name _;

    location / {
        proxy_pass http://172.32.0.11:8080;

        client_max_body_size 32m;
        proxy_request_buffering off;
    }
}
```

```bash
$ nginx -t && systemctl reload nginx
$ curl -s --data-binary @/root/upload-25m.bin http://127.0.0.1/upload
stored bytes=26214400
$ printf 'rejected_by: proxy\nlimit_bytes: 1048576\n' > /root/answers/upload.md
```

</details>

## Carrying this forward

- **A limit at a round number is a setting.** 1 MB, 10 MB, 30 seconds, 100
  connections — go and find the config, do not go looking for a resource.
- **Ask whether the next hop ever saw the request.** An upstream with no record
  of it did not reject it. This one question separates proxy faults from
  application faults faster than any log.
- **Raise limits; do not remove them.** `0` for a body size, `off` for a
  timeout, unlimited anything — those turn a bounded failure into an unbounded
  one, and the unbounded one arrives at 3 a.m.
- **Know where the body is while it is in flight.** Buffered means a file on the
  proxy and an upstream that has heard nothing yet. Streamed means an upstream
  connection held open for as long as the client feels like taking.
- **The defaults are opinions about a different service.** `client_max_body_size
  1m` and `proxy_request_buffering on` are good defaults for a site that does
  not take uploads. They are the wrong ones for the route that does.
