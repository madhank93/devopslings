## What you'll be able to do

- Read a 403 from nginx as a statement about a process, a user, and a path,
  and find which component of the path is the one that refuses
- Reason about `proxy_pass` well enough to predict what the upstream receives
  before you reload
- Tell a dead upstream from a slow one, and fix each at the end that is
  actually broken
- Write a health check that reflects whether the node can do its job, rather
  than whether it is running
- Cache aggressively without serving yesterday's deploy
- Keep a rate limiter and an access log honest about which client a request
  came from, across a proxy hop

## Why these

Everything here sits between a user and an application, which makes it the
place where blame is hardest to assign. The application logs a request it never
received. The proxy logs a response it never got. The dashboard shows an error
rate and no side of the boundary.

The habit this module builds is asking what the *next* hop saw. A request that
looks correct leaving the client can be wrong by the time the upstream reads it,
and the difference is almost always visible in one line of configuration.

## Before you start

Modules 01 and 05. This module runs `web-stack`: a proxy, an upstream and a
client, on three separate boxes, because a proxy failure with no hop in it is
not a proxy failure.
