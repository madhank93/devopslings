## What you'll be able to do

- Read an `EXPLAIN (ANALYZE, BUFFERS)` plan and say where the estimate went wrong
- Recognise why an index that exists is not being used, and fix the cause
- Find the query that is slow in aggregate but fast individually
- Identify what a blocked migration is waiting on, from `pg_locks` and
  `pg_stat_activity`
- Quantify replication lag, and reason about read-your-writes without sending
  every read to the primary
- Choose eviction and persistence policies per keyspace, rather than per server
- Justify every index on a table against a query, and measure what the rest
  cost on the write path
- Recognise a deadlock as a property of a pair of code paths, and remove it by
  making lock acquisition order consistent
- Tell atomicity and isolation apart, and pick between a row lock and a
  serialization retry on measured cost
- Find what is holding the vacuum horizon — an old snapshot, a replication
  slot, or a prepared transaction — and know which of the three has no session
  to kill
- Tell a hot shard from a capacity problem, and choose a shard key that spreads
  the writes without turning the common read into a scatter-gather
- Set a read and a write quorum so a read sees the write before it, and say why
  R + W > N is the line that decides it
- Read an LSM write stall as back-pressure from compaction falling behind, and
  tune flush rate against compaction rate rather than raising the threshold
- Choose a store per workload on the access pattern, the consistency it needs,
  the durability it does not, and the cardinality it carries
- Triage a slow, timing-out request by asking in order — is it waiting (and on
  whom, or on no session at all), is the replica replaying, and what plan does
  it get — before touching the app

## The sandbox

`db-stack` is a Postgres primary and a streaming replica, pgbouncer in front of
the primary, a Redis, and an idle container holding an LSM engine. The `orders`
table is seeded with ten million rows.

That seed is the point rather than showing off. On a thousand rows the planner
picks a sequential scan no matter what you index, so a small database would
teach the opposite of most of this module.

First start pays for the seed — expect a couple of minutes and roughly 2 GB.
After that it comes up in well under a minute.

```
devopslings start read-the-plan
```

| what | where |
|---|---|
| primary | `localhost:15432` |
| replica | `localhost:15433` |
| pgbouncer | `localhost:16432` |
| redis | `localhost:16380` |
| lsm | no port — `devopslings shell lsm-write-stall` |

The database is `shop`, the superuser is `postgres` / `devopslings`.

## Postgres, and where the ideas transfer

The mechanisms here are Postgres-specific and the reasoning is not. Every
engine has a planner that can be wrong about row counts, a way to make an index
unusable by wrapping the column in a function, a lock queue where one idle
transaction stalls everything behind it, and a replica that is behind. The
commands change; the questions do not.
